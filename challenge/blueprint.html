01Problem

Every knowledge worker has a repeating task. Nobody has an agent that gets better at it.

Generative AI tools are available in most organisations. Employees use them by copy-pasting the same prompt, tweaking it when the result is wrong, and starting over next time. Nothing is saved. Nothing improves.

Who lives with it
Knowledge workers in HR, legal, finance, operations and customer service who produce the same type of structured output — reports, response emails, briefings, summaries — repeatedly, from company documents and internal data.
What happens today
The employee opens a chat interface, pastes their prompt, reads the result, edits the prompt, pastes it again. When the result is finally good, the improved prompt is forgotten. The cycle repeats next time.
What it costs
Time lost to prompt iteration on every run, accumulated across every knowledge worker who does this daily. The agent that already knows what 'good' looks like for this person and this task does not exist yet.
Why now
LLMs are good enough to generate and accept prompt improvements from plain-language feedback. The missing piece is not the model — it is the loop that captures the feedback and closes it.

03Architecture

watsonx.ai is the engine and the coach — Bob is where it is built

The studio is three screens over a single agent loop. watsonx.ai runs the agent and generates the improvement suggestion. Company knowledge is a grounding context, not a fine-tuned model.

Dashed nodes are mocked in the proof of concept with synthetic data and invented policy docs. Interfaces are the real ones — the mock is swapped for the live system in the pilot.

IBM technology in this solution

  • Agent runner — Executes the agent with grounded instructions on each run — FastAPI /run endpoint
  • Improvement engine — Turns a rating + comment into a concrete, actionable prompt edit suggestion — FastAPI /improve endpoint
  • Bob IDE — Build environment: all code written in Bob; task session report is submission evidence

Grounding, not fine-tuning

Company knowledge is passed as context on each run. No model is fine-tuned, so the PoC runs without data export approval and the knowledge stays current without retraining.

Improvement is a suggestion, not an automatic rewrite

The agent never updates its own instructions without the user's explicit acceptance. This keeps a person in the loop and avoids drift.

Mocks behind real interfaces

The PoC runs on synthetic data. The policy store, email connector and CRM expose the same API the real systems would, so the mock is replaced by an adapter in the pilot without changing the agent.

Built entirely in Bob

The task session report in Bob IDE is part of the submission. Building outside Bob loses that evidence for the judges.

What is different here

Every alternative on the list produces an output. Only this solution closes the loop: when the output is wrong, the agent proposes a change to its own instructions, the user accepts or edits it, and the next run starts better. That loop — feedback to suggestion to acceptance to improved run — is absent from every listed alternative and from most commercial agent builders.

06Demo

Three minutes, one complaint, the agent rewrites itself on screen

One customer service manager (CMP-0001). The audience watches a too-formal reply become a human one — after one star rating and one sentence of feedback. No code. No IT ticket.

  1. 1

    Empty state → first agent0:00–0:45

    Manager opens studio, names the agent 'Customer Complaint Handler', picks three fields (input: complaint, context: service policy, output: email draft + action note), clicks Generate. Steps appear. Clicks Run.

  2. 2

    First run — too formal0:45–1:30

    CMP-0001 complaint pasted. Draft arrives in 3–5 s. Opening line: 'Dear Customer, I am writing to acknowledge...' — the audience recognises the problem. Google Gemini powers the run.

  3. 3

    Rate → improvement suggestion1:30–2:20

    Manager clicks 2 stars, types 'Too formal — use their first name and be more empathetic'. Clicks Get improvement suggestion. Studio shows: 'Add step: address customer by first name; open with direct acknowledgment of frustration.' Manager clicks Accept.

  4. 4

    Second run — the aha moment2:20–2:50

    Same complaint. New run. Draft opens with the customer's first name and leads with empathy. The room sees the difference without being told. Two seconds of silence here.

  5. 5

    Saved — loop closes2:50–3:00

    Manager clicks Save. Back on home — agent card appears. The accepted improvement is now in the agent's instructions permanently. Every future run starts from this better baseline.

07Adoption

A knowledge worker is productive in the first five minutes

No IT request. No training course. The agent builder is three fields and a Run button. The first useful output arrives before the employee finishes reading the instructions.

  1. 1

    Open the studio

    Link in the company intranet or a pinned message in the team channel. No install, no new login.

  2. 2

    Describe your task in plain language

    Three fields: what you will give it, what you want back, which company doc it should follow. Each field has a placeholder example.

  3. 3

    Run it once

    Paste your real input — a complaint, a note, a request — and click Run. The first output arrives in seconds.

  4. 4

    Rate and let it improve

    If the result is not quite right, give it stars and a comment. Accept the suggestion. Run again. Three iterations are typical before the agent matches your standard.

  5. 5

    Reuse tomorrow

    The agent is saved with your name. Tomorrow it starts from where you left it — the improvements are already in.
